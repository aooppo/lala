# Feature Specification: Candidate 16 Keyframe Publish

**Feature Branch**: `codex/lady-lala-pilot-live`

**Created**: 2026-08-21

**Status**: Approved for implementation

**Input**: Record the Owner's three Candidate 16 keyframe selections, promote their exact bytes, publish one role-complete keyframe set, bind Goal 2 to it, record the later explicit Candidate 16 V7-B winner review, advance only after all provenance/hash gates pass, and prove a motion-only Coffee Table plan with zero provider calls while stopping before paid Live authorization.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Approve and Promote One Keyframe per Role (Priority: P1)

As the project owner, I can record my explicit selection of one reviewed Candidate 16 image for each production role and promote only those exact bytes into approved authority.

**Why this priority**: No downstream set or video plan may claim Candidate 16 authority until all three human decisions and exact-byte promotions are proven.

**Independent Test**: Start from the immutable seven-row V2 review package, record the three authorized selections, validate exactly one passing selection per role, and prove staged and approved hashes match while all non-selected media and historical evidence remain unchanged.

**Acceptance Scenarios**:

1. **Given** the V2 manifest and files match the authorized IDs, roles, and hashes, **When** the Owner decision is recorded, **Then** only K1-V2-002, K2-002, and K3-V2-002 have role-applicable PASS decisions, attributable reviewer data, and timezone-aware review time.
2. **Given** a complete valid review, **When** each selected candidate is promoted, **Then** its approved bytes exactly match its staged bytes and its promotion evidence identifies Candidate 16 and the correct role.
3. **Given** a hash, role, review, active-character, selection-count, or collision mismatch, **When** validation or promotion is attempted, **Then** the operation fails closed without overwriting approved or historical evidence.

---

### User Story 2 - Build and Publish a Candidate 16 Keyframe Set (Priority: P1)

As the video operator, I can build one immutable role-complete Candidate 16 keyframe set and explicitly publish it as the current Goal 2 visual authority.

**Why this priority**: Three independent approved files are insufficient unless their shared character identity, role mapping, provenance, and current published status are unambiguous.

**Independent Test**: Build a set from the three approved selections, verify all character/review/hash gates, publish it, and resolve one current published-set pointer without changing any set manifest or prior event.

**Acceptance Scenarios**:

1. **Given** exactly one approved K1, K2, and K3 bound to the active Candidate 16 character, **When** a set is built, **Then** one versioned immutable manifest records set identity, character, role members, hashes, provenance, set hash, and creation time.
2. **Given** a valid unpublished set and explicit Owner publish authority, **When** it is published, **Then** an append-only publish event is recorded and one collision-safe current pointer advances by revision.
3. **Given** missing, ambiguous, mixed-character, drifted, unreviewed, or already-colliding inputs, **When** build or publish is attempted, **Then** it fails without partial manifests, events, or pointer changes.

---

### User Story 3 - Rebind and Preflight Goal 2 (Priority: P1)

As the production operator, I can bind Goal 2 to the active Candidate 16 character and its current published keyframe set, while distinguishing reusable motion methodology from identity-bound validation evidence.

**Why this priority**: Goal 2 must not silently retain legacy Lady LaLa identity authority or misrepresent old character-bound evidence as Candidate 16 validation.

**Independent Test**: Resolve Goal 2 after publish and verify Candidate 16, all three selected roles and hashes, and provenance; classify the V7 prerequisite without altering historical V7 evidence.

**Acceptance Scenarios**:

1. **Given** a current published Candidate 16 set, **When** Goal 2 is rebound and preflighted, **Then** it resolves the active Candidate 16 character and the exact K1/K2/K3 selections with matching hashes and provenance.
2. **Given** legacy current identity fields, **When** the new binding resolves, **Then** legacy Lady LaLa sources remain historical but cannot serve as current Candidate 16 authority.
3. **Given** V7 methodology that is character-independent, **When** prerequisites are evaluated, **Then** only the methodology is reusable; any character-bound media remains attributable to its original character and triggers a precise authorization blocker if a Candidate 16 rerun is required.

---

### User Story 4 - Preview a Motion-Only Coffee Table Campaign (Priority: P2)

As the production operator, I can validate a 15–20 second Candidate 16 Coffee Table campaign brief and delivery plan without dialogue, speech synthesis, lip sync, network traffic, or paid provider submission.

**Why this priority**: The next owner decision requires a truthful, costed production plan after visual authority is ready, not an unauthorized live generation.

**Independent Test**: Run the Coffee Table dry-run and inspect evidence for Candidate 16, the published set, product IN3725/PDP provenance, Henry scene/performance requirements, motion-only semantics, 1:1 and 9:16 delivery, and zero provider accounting.

**Acceptance Scenarios**:

1. **Given** Goal 2 is ready, **When** the Coffee Table dry-run runs, **Then** it records the specified product, room, wardrobe, wine-glass performance, product-hero storyboard, and current Candidate 16 keyframe binding.
2. **Given** the brief is motion-only, **When** the plan resolves, **Then** it contains no talking, dialogue, speech synthesis, lip-sync task, or talking-provider dependency.
3. **Given** requested 1:1 and 9:16 delivery, **When** the plan resolves, **Then** it states a safe master and reframing strategy or identifies native-ratio generation when safe reframing cannot preserve the character, glass, and product.
4. **Given** dry-run mode, **When** validation completes, **Then** provider submissions and paid calls both remain exactly zero while a bounded live cost projection is reported but not executed.

---

### User Story 5 - Close Candidate 16 V7 Human Review (Priority: P1)

As the project owner, I can record V7-B Natural Micro Motion as the unique Candidate 16 stability winner, preserve A/C as explicit non-selections, and register the reviewed evidence so Goal 2 can advance without any new provider call.

**Why this priority**: Coffee Table planning must depend on the exact Candidate 16 V7 media, tasks, prompts, keyframe, and latest human decision rather than the legacy Lady LaLa V7 run or an automatic quality claim.

**Independent Test**: Starting from the immutable Candidate 16 parent/recovery runs and review package, record the supplied three-row decision, validate all media/task/prompt/keyframe hashes, register V7-B, obtain `GOAL2_READY`, execute the Coffee Table dry-run, and verify the final state is `READY_FOR_COFFEE_TABLE_LIVE_AUTHORIZATION` with zero new calls.

**Acceptance Scenarios**:

1. **Given** the exact Candidate 16 V7 review package, **When** the Owner decision is recorded, **Then** V7-B contains every supplied applicable PASS including teeth and MTL readiness, while V7-A and V7-C are explicitly not selected with the supplied reasons and false overall readiness.
2. **Given** the split parent/recovery evidence, **When** registration runs, **Then** it joins inherited A with recovered B/C, verifies all three task IDs, media hashes, prompt hashes, the Candidate 16 K1 hash, blank append-only run reviews, human attribution, and exactly one passing winner before writing collision-safe registration evidence.
3. **Given** a valid V7-B registration, **When** Goal 2 preflight runs, **Then** it returns `GOAL2_READY` and identifies V7-B as the reviewed Candidate 16 motion baseline.
4. **Given** Goal 2 readiness, **When** Coffee Table dry-run completes, **Then** it writes the bounded motion-only plan and stops at `READY_FOR_COFFEE_TABLE_LIVE_AUTHORIZATION` without `--live`, provider construction, submission, task creation, or paid calls.

### Edge Cases

- A selected file matches its manifest entry but its bytes no longer match the authorized SHA.
- Two reviewed candidates claim the same role, or a selected candidate has the wrong formal role.
- An approved target, set ID, publish event, or current pointer revision already exists.
- Active character changes between validation and mutation, or set members reference mixed characters.
- A crash occurs after exact-byte copy, set-manifest creation, event creation, or before pointer replacement.
- Historical V7 methodology is reusable but its media/hash is tied to the former Lady LaLa identity.
- A delivery crop would remove Candidate 16's face/body, the wine glass, or the Coffee Table.
- Any dry-run path accidentally attempts to construct or submit a live provider request.
- The Candidate 16 V7 evidence is split across an A-success parent and a B/C-success recovery run.
- A review attempts to pass more than one winner, omits teeth or another supplied V7-B decision, changes A/C provenance, or uses a naive timestamp.
- The review package media are intact but no longer match the task/artifact hashes in the parent/recovery evidence.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The workflow MUST recompute and validate each authorized candidate's ID, role, path, and SHA-256 against both the V2 manifest and actual bytes before recording review or promotion.
- **FR-002**: The review MUST record literal PASS only for role-applicable required human fields on the three selected rows, plus the exact reviewer identity, timezone-aware review time, and Owner notes; non-selected subjective fields MUST remain blank unless an existing formal state supports selection metadata.
- **FR-003**: Review validation MUST require exactly one passing, video-ready selected candidate for each of the home-context, talking-medium-closeup, and product-present roles.
- **FR-004**: Promotion MUST copy exact bytes, verify staged/approved hashes, record truthful review and character provenance, reject overwrite/collision, and leave non-selected candidates untouched.
- **FR-005**: All three approved role authorities MUST resolve to the currently active `character-20260821-001` Candidate 16 profile before a set can be built.
- **FR-006**: Set build MUST create one immutable, versioned manifest containing set ID, version, character identity, exactly one K1/K2/K3 member, candidate IDs, roles, approved paths/hashes, review and promotion provenance, creation time, and a deterministic manifest hash.
- **FR-007**: Set build MUST fail closed on missing, ambiguous, mixed-character, inactive-character, drifted, unreviewed, or colliding authority without leaving a partial authoritative set.
- **FR-008**: Publish MUST require explicit authority and a passing integrity gate, append an immutable publish event, and atomically advance one revisioned current published-set pointer without rewriting prior manifests or events.
- **FR-009**: Repeated build or publish attempts MUST be collision-safe and MUST NOT silently overwrite or duplicate authoritative evidence.
- **FR-010**: Goal 2 MUST resolve its current identity authority from the active character and current published keyframe set, preserving separate K1 motion, K2 talking, and K3 product roles and their hashes/provenance.
- **FR-011**: Goal 2 preflight MUST fail before run allocation or provider construction when the character, published set, member hashes, roles, review provenance, or current binding is missing, ambiguous, stale, or inconsistent.
- **FR-012**: V7 evaluation MUST distinguish character-independent methodology from character-bound media evidence and MUST never relabel old Lady LaLa validation as Candidate 16 evidence.
- **FR-013**: The Coffee Table brief MUST bind product `IN3725`, its supplied PDP, Candidate 16, the published K1/K2/K3 set, the Henry room, red wardrobe continuity, wine-glass action, and product-hero ending.
- **FR-014**: The Coffee Table workflow MUST be motion-only and MUST NOT add dialogue, talking video, speech synthesis, or lip sync.
- **FR-015**: The Coffee Table plan MUST represent an approximately 15–20 second six-beat storyboard and planned 1:1 plus 9:16 delivery without unsafe automatic cropping.
- **FR-016**: Coffee Table dry-run MUST make zero network/provider submissions and zero paid calls while producing a bounded provider/model/task/duration/credit/USD live projection.
- **FR-017**: All mutations MUST preserve approved-source immutability, V1/V2 generated media, PDP references, historical Lady LaLa/V7 evidence, and append-only run evidence.
- **FR-018**: Failures MUST report a precise integrity, semantic, V7 authorization, or external-readiness blocker without automatic paid retry or fallback generation.
- **FR-019**: The Candidate 16 V7 review MUST record `v7-b-natural-micro-motion` as the unique fully passing and MTL-ready winner, including PASS for visual identity, face, age, hair, body proportions, wardrobe, jewelry, mouth, teeth, eyes, background, motion, and technical export.
- **FR-020**: V7-A MUST remain not selected for excessive subject position/scale movement, and V7-C MUST remain not selected as an acceptable fallback that loses to B's balance; their formal MTL readiness MUST be false.
- **FR-021**: V7 registration MUST validate the Candidate 16 K1 identity, parent/recovery relationship, canonical A/B/C order, provider task IDs, exact media/prompt hashes and paths, blank append-only reviews, exact review schema/provenance, unique winner, human reviewer, and timezone-aware review time before Goal 2 readiness.
- **FR-022**: V7 registration MUST create separate collision-safe evidence and MUST NOT rewrite parent/recovery runs, media, prompts, approved keyframes, or the original review-package manifest.
- **FR-023**: Goal 2 preflight MUST use the validated current Candidate 16 V7 registration in preference to legacy V7 classification and expose the selected V7-B evidence.
- **FR-024**: This authorized continuation MUST execute only review recording, V7 registration, Goal 2 preflight, Coffee Table dry-run, and exact non-executed Live/cost planning, stopping at `READY_FOR_COFFEE_TABLE_LIVE_AUTHORIZATION`.

### Key Entities

- **Owner Keyframe Review**: Candidate-bound role-specific human decisions and attribution for the immutable V2 package.
- **Approved Role Authority**: Exact-byte approved Candidate 16 keyframe and its review/promotion provenance for K1, K2, or K3.
- **Keyframe Set**: Immutable versioned collection of exactly one approved authority for each production role, all bound to one character.
- **Publish Event**: Append-only evidence that an authorized set passed gates and became current.
- **Published-Set Pointer**: Revisioned current-state reference to exactly one published set.
- **Goal 2 Binding**: Resolved active character and published role authorities used by downstream video preflight.
- **Coffee Table Brief**: Motion-only product, scene, performance, storyboard, ratio, and cost-plan evidence.
- **Candidate 16 V7 Registration**: Collision-safe evidence joining the explicit V7-B decision to the exact Candidate 16 parent/recovery tasks, media, prompts, and K1 hash.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Exactly three and only three selected rows validate—one per K1/K2/K3 role—with attributable timezone-aware Owner PASS decisions.
- **SC-002**: Each of the three promotions has identical staged and approved SHA-256 values, and zero non-selected images are promoted.
- **SC-003**: One Candidate 16 v1 keyframe set contains exactly three role-unique members and passes 100% of character, hash, review, provenance, and ambiguity gates.
- **SC-004**: Publish produces one immutable event and advances one current pointer revision while all prior authoritative records remain byte-for-byte unchanged.
- **SC-005**: Goal 2 preflight resolves Candidate 16 and the exact three Owner selections with no current legacy Lady LaLa identity authority.
- **SC-006**: The Coffee Table dry-run records all required product, scene, action, storyboard, and ratio semantics with zero talking/TTS/lip-sync work.
- **SC-007**: Dry-run provider submissions and paid calls equal zero, and the proposed live plan reports bounded tasks, seconds, credits, USD, and delivery strategies.
- **SC-008**: Full offline tests, focused tests, source validation, compilation, diff checks, hash/integrity comparison, and secret scans pass without changing historical media evidence.
- **SC-009**: Exactly one Candidate 16 V7 row is fully passing and MTL-ready—V7-B—and 100% of A/B/C task, media, prompt, keyframe, review, and parent/recovery gates pass.
- **SC-010**: Goal 2 reports `GOAL2_READY`, Coffee Table dry-run reports `READY_FOR_COFFEE_TABLE_LIVE_AUTHORIZATION`, and new provider submissions, task IDs, HTTP calls, and paid calls all equal zero.

## Assumptions

- The supplied candidate IDs, roles, and expected hashes are the explicit Owner selections, but actual bytes and manifest data remain authoritative and must be revalidated.
- `character-20260821-001` is expected to remain the sole active character throughout build and publish; any change fails closed.
- Non-selected review rows retain blank subjective fields because the current review contract has no invented `NOT_SELECTED` decision.
- One safe high-quality master with local reframe-aware variants is preferred; native ratio generation is planned when safe reframing cannot preserve the key composition.
- This feature authorizes local evidence mutations and dry-run planning only; it does not authorize any new media generation, live Coffee Table call, additional variation, or paid retry.
- The owner's current request is the sole authority for the V7-B review decisions and the offline continuation boundary.
